# Kairos MVP 2.0 可执行版本计划

本文把 MVP 2.0 拆成可独立验收、可回滚的增量版本。实现顺序以服务端控制面、同步协议、客户端数据迁移、协作和管理后台为主线，避免一次升级同时替换身份、权限和同步三个高风险边界。

## 1. 当前基线与目标

当前版本是 Flutter 离线优先客户端、Go HTTP/WebSocket 服务端和 PostgreSQL 单账号同步系统。数据库中任务、标签、项目、清单、困难点、同步操作和变更游标均直接按 `user_id` 隔离；Redis、群组、花名册、管理会话和管理页面尚未实现。

MVP 2.0 的交付目标如下：

- 保留一人一个可登录真实账号，每个真实账号自动拥有一个个人工作空间。
- 一个真实账号可加入多个群组，并在个人任务和多个群组任务间快速切换。
- 群组保留独立花名册。花名册中的群组账号不能登录，可以先创建、后绑定真实账号。
- 普通邀请码可按时间和次数独立限制；花名册认领邀请码绑定指定群组账号且强制单次使用；任何邀请码最长有效 30 天。
- PostgreSQL 保存权威业务状态，Redis 承担限流、管理会话、缓存和多实例实时通知。
- 使用作用域明确的 L1/L2/L3 角色，不在首版引入权限码。
- 群组协作默认关闭，开启后不可关闭；历史任务不会因开关变化而自动共享。
- 以 Go `embed.FS` 提供原生 HTML/CSS/JavaScript 的 `/KairosAdmin/` 管理后台。

本轮不包含群组层级嵌套、自定义角色、细粒度权限码、跨群组共享、外部身份提供商、公开注册审批流、计费和云端多实例编排平台。

## 2. 已确定的领域模型

### 2.1 身份、工作空间和花名册

建议使用显式成员关系，而不是复制可登录用户：

| 实体 | 责任 | 关键约束 |
| --- | --- | --- |
| `users` | 可登录的真实账号 | 服务器内唯一；停用后不能登录或刷新会话 |
| `workspaces` | 所有任务数据的隔离边界 | 类型只能是 `personal` 或 `group` |
| `groups` | 群组资料和策略 | 与一个群组工作空间一一对应 |
| `group_accounts` | 群组花名册条目 | 不能登录；同一群组内使用稳定编号或名称 |
| `group_account_links` | 真实账号与花名册的绑定历史 | 同一时刻一个群组账号至多绑定一个真实账号；一个真实账号在同一群组至多绑定一个群组账号 |
| `group_invites` | 邀请策略和使用计数 | 只存邀请码摘要；原始邀请码只在创建时返回 |
| `group_invite_redemptions` | 邀请兑换与幂等记录 | 每次成功兑换唯一且可审计 |
| `audit_events` | 管理和安全审计 | 仅追加，不通过普通业务接口修改或删除 |

“加入群组”等价于存在有效的 `group_account_links` 记录。解绑只结束当前绑定，不删除群组账号、历史绑定、任务归属或审计记录。这样既保留花名册，也避免创建第二套可登录的“虚拟用户”。

### 2.2 角色模型

| 角色 | 存储位置 | 能力边界 |
| --- | --- | --- |
| 独立成员 L1 | 真实账号的个人工作空间隐式获得 | 只管理自己的个人任务，不参与角色分配 |
| 群组成员 L1 | 当前有效的群组账号绑定 | 使用该群组内被授权的数据，不参与角色分配 |
| 群组管理员 L2 | 群组账号角色 | 仅管理自己具有 L2 身份的群组，可授予 L1 或 L2 |
| 超级管理员 L3 | 真实账号的服务器级角色 | 管理服务器内全部账号、群组和角色，可授予 L1、L2 或 L3 |

“可分配小于等于自身等级”是角色分配的上限，不代表 L1 自动拥有角色管理能力。所有角色变更同时检查等级和作用域。L2 不能创建或授予 L3，也不能管理其他群组；L3 的服务器级能力不能由群组角色推导。

必须保留最后一个有效 L3；群组保留至少一个有效 L2，除非由 L3 接管或群组进入归档流程。降级、停用、解绑、重绑和角色变更均写入审计日志。

### 2.3 邀请码规则

- `expires_at` 必填，必须晚于服务器当前时间，且不得超过创建时间后 30 天。
- `max_uses = NULL` 表示在有效期内不限次数；正整数表示最多成功兑换次数。
- 时间限制和次数限制同时存在时，任一条件触发即失效。
- 指定 `target_group_account_id` 时强制 `max_uses = 1`，目标必须属于同一群组且当前未绑定。
- 普通邀请码成功兑换时，在同一事务内创建群组账号和有效绑定。
- 只有完整绑定成功后才增加使用次数；请求重试使用幂等键返回原结果，不重复计数。
- 兑换事务使用行锁复查撤销、过期、次数、成员关系和花名册绑定状态，防止并发超额。
- 邀请码可在到期前主动撤销，但不能恢复；日志和兑换记录不随撤销删除。

### 2.4 Redis 边界

PostgreSQL 是账号、群组、绑定、角色、邀请计数、协作开关和审计的唯一权威来源。Redis 不保存无法从 PostgreSQL 或运行状态重建的唯一业务事实。

Redis 用于登录与邀请兑换限流、KairosAdmin 会话、短期查询缓存和多实例 WebSocket Pub/Sub。Redis 不可用时：已认证的个人任务读写和同步继续工作；依赖防重放或管理会话的敏感操作失败关闭并返回 `DEPENDENCY_UNAVAILABLE`；就绪检查报告 `degraded`，但不得谎报数据库不可用。

### 3.1 `v2.0.0-alpha.1`：工程基线与 Redis

实施内容：

- 统一服务端配置校验、结构化日志、请求 ID、稳定错误响应和优雅停机。
- 增加 Redis 客户端抽象、连接池、超时、健康状态和测试替身。
- 扩充本地部署 Compose、环境变量示例、systemd 与 Nginx 文档，不提交真实密码或令牌。
- CI 增加 Redis 服务、迁移升降级检查、Go `fmt`/`vet`/单元测试、PostgreSQL/Redis 集成测试和 Flutter 既有门禁。
- 记录数据库、Redis、同步延迟、登录失败和邀请兑换的基础指标，不记录密码、令牌或原始邀请码。

验收门禁：Redis 正常、超时和断连三种状态可重复测试；Redis 断连不会造成个人任务数据丢失；配置缺失时服务拒绝以不安全默认值启动。

回滚：服务端退回旧二进制即可；此阶段不写入新业务数据，不依赖破坏性数据库迁移。

### 3.2 `v2.0.0-alpha.2`：身份、群组、花名册与 RBAC

实施内容：

- 增加 `workspaces`、`groups`、`group_accounts`、`group_account_links`、服务器级角色和 `audit_events` 表。
- 为每个现有真实账号创建唯一的个人工作空间，并建立不可删除的所有权关系。
- 增加用户状态、群组状态、群组创建、花名册增删改、绑定、解绑、重绑和角色分配服务。
- 所有写操作以数据库约束兜底：活动绑定使用部分唯一索引，角色使用枚举或检查约束，最后管理员保护放在事务中执行。
- API 授权不信任客户端提交的角色或群组；每次请求从有效绑定和服务器角色重新计算权限。
- 提供一次性 L3 引导命令或部署参数，引导完成后不可通过普通启动流程重复创建 L3。

验收门禁：同一人可加入多个群组但不能在同一群组重复加入；同一花名册账号不能被并发绑定两次；L2 不能跨群组操作或授予 L3；最后一个 L2/L3 保护在并发请求下仍成立。

回滚：保留新增表和数据，回退代码时只关闭新路由；已产生群组数据后禁止执行破坏性 down migration。

### 3.3 `v2.0.0-alpha.3`：邀请码与审计

实施内容：

- 增加邀请和兑换表，邀请码使用至少 128 位随机熵，只存带服务端密钥的摘要。
- 实现普通邀请码、指定花名册认领邀请码、撤销、列表和兑换接口。
- 创建接口同时验证 30 天上限、使用次数、目标群组账号、创建者等级和群组作用域。
- 兑换使用 PostgreSQL 单事务和行锁；Redis 只做请求限流，不能代替数据库次数判断。
- 管理审计记录操作者、作用域、动作、目标、结果、请求 ID、时间和必要的前后状态摘要，敏感字段脱敏。

验收门禁：覆盖 30 天边界、服务器时钟、无限次、单次、指定次数、撤销、重复提交、已是成员、目标已绑定和高并发最后一次兑换；原始邀请码不能从数据库、日志或列表 API 恢复。

回滚：停用邀请创建和兑换路由；保留邀请、绑定及审计数据，已完成的成员关系不自动撤销。

### 3.4 `v2.0.0-alpha.4`：工作空间同步 v2

实施内容：

- 为任务、标签、项目、清单分组、困难点、任务标签、同步操作和变更日志增加 `workspace_id`。
- 群组任务额外记录花名册归属、创建者真实账号和最后操作者；任务可见性为后续协作预留明确字段。
- 迁移现有记录到各自的个人工作空间，再逐步设置非空约束和按工作空间重建唯一索引。
- 实现 `/api/v2/workspaces/{workspace_id}/sync/*`，快照、增量游标、幂等键、冲突检测和实体引用全部校验工作空间。
- WebSocket 只发送含 `workspace_id` 和游标的变更提示，不直接广播任务正文。
- 暂时保留 `/api/v1`，将旧请求映射到当前用户的个人工作空间，避免旧客户端立即失效。

验收门禁：构造相同实体 ID、标签名、操作 ID 和游标并验证不同空间互不影响；越权 ID 返回统一的作用域错误；撤销成员后立刻停止该空间同步；v1 个人同步回归测试全部通过。

回滚：在 v2 客户端成为主版本前可回退到兼容服务端；一旦新客户端写入群组数据，只允许代码回滚，不能删除 `workspace_id` 或恢复旧唯一索引。

### 3.5 `v2.0.0-beta.1`：Flutter 多群组与离线隔离

实施内容：

- Drift 本地库加入工作空间、成员身份、每空间游标、每空间 outbox 和撤权恢复区。
- 首次升级先为旧数据填入个人工作空间；完成一次 v2 快照校验前不删除或重写旧数据。
- 在宽屏导航和移动端任务页提供稳定尺寸的工作空间选择器，显示“个人任务”和已加入群组，记住最近空间。
- 任务仓储、筛选条件、标签、项目、清单、冲突和实时订阅均以当前 `workspace_id` 为必需参数。
- 切换空间先切换本地查询，再独立触发该空间同步；一个空间失败不阻塞其他空间。
- 成员被解绑时，将未推送操作放入只读恢复区，允许导出或复制回个人空间，禁止继续上传。
- 增加邀请码兑换入口和兑换后的空间刷新，不在客户端自行判断最终权限。

验收门禁：Windows 与 Android 均可在离线状态快速切换多个空间；相同名称和 ID 不串数据；切换期间无上一空间短暂闪现；被移除成员的本地修改不会重新上传；升级失败可以保留原数据库恢复。

回滚：保留旧本地表或迁移备份直到 v2 快照成功；应用回退时只允许继续访问个人空间，不静默丢弃群组本地数据。

### 3.6 `v2.0.0-beta.2`：协作与 KairosAdmin

实施内容：

- `groups.collaboration_enabled_at` 只能从空变为非空，数据库触发器或等价约束拒绝清空和回拨。
- 开启协作要求二次确认，展示不可逆含义，并写入审计事件；开启不改变任何已有任务的可见性。
- 增加显式共享操作和共享任务协作规则；每次读取、写入和同步均校验成员状态、任务可见性和角色作用域。
- 使用 `embed.FS` 提供原生 HTML/CSS/JavaScript 页面，不增加 Node 构建链。
- 只注册大小写敏感的 `/KairosAdmin/` 和其静态资源路径；`/admin/`、`/Admin/` 及其他大小写变体返回 404。
- KairosAdmin 使用 HttpOnly、Secure、SameSite=Strict Cookie，会话存 Redis；所有写请求使用 CSRF token，并配置 CSP、点击劫持防护、限流和安全审计。
- L3 可管理服务器账号、群组、花名册和角色；L2 只看到自己管理的群组，不能枚举服务器账号，绑定时只允许按精确账号标识查询。

验收门禁：协作开关无法通过 API、数据库更新或并发请求关闭；未显式共享的历史任务保持原可见性；L2 无法通过修改 URL 或请求体访问其他群组；管理登录、CSRF、会话过期、账号停用、Redis 断连、CSP 和入口大小写均有自动化测试。

回滚：后台可整体关闭路由；协作一经开启不得因代码回滚写回关闭状态，旧服务端若不理解协作字段则禁止部署。

### 3.7 `v2.0.0-rc.1`：迁移与正式发布门禁

实施内容：

- 以脱敏生产规模数据演练 `pg_dump`、迁移、校验、代码回滚和灾难恢复，记录恢复时间和恢复点。
- 完成 PostgreSQL/Redis 并发集成测试、API 授权矩阵测试、Flutter 单元/组件/集成测试、Windows 发布构建和 Android 构建。
- 增加升级前检查：数据库版本、可用空间、备份成功、Redis 连通性、唯一约束冲突和最后管理员状态。
- 更新部署、监控、告警、密钥轮换、L3 恢复、账号停用、成员移除和邀请泄露处置手册。
- 收集至少一个完整预发布周期的错误率、同步延迟、Redis 降级和迁移指标，再决定 `v2.0.0` 发布。

正式发布条件：不存在跨空间数据泄漏或角色越级的已知缺陷；迁移和恢复演练通过；旧客户端兼容窗口及 `/api/v1` 退役日期已经公布；所有待确认的 P0 产品边界已有决策记录。

## 4. 数据迁移与兼容策略

采用 expand/migrate/contract 三段式迁移：

1. Expand：只新增表、可空列和兼容索引，服务端仍能处理 v1 个人空间请求。
2. Migrate：为现有用户创建个人工作空间，分批回填所有实体和同步记录的 `workspace_id`，校验数量、引用和摘要。
3. Contract：新旧服务端均不再需要旧结构后，才设置非空约束、替换唯一索引并停止双写；删除旧列放到 MVP 2.0 之后的独立版本。

上线顺序固定为：备份与预检、兼容迁移、兼容服务端、v2 客户端、观察期、约束收紧。回滚优先回滚应用代码，不对已经承载新数据的数据库执行 down migration。

## 5. 全程测试与安全门禁

- 数据库：迁移空库、v1 样本库和大数据量样本库；验证升级幂等、外键、部分唯一索引、不可逆协作和备份恢复。
- 授权：使用主体、角色、群组、资源和动作组成表驱动矩阵，覆盖允许、拒绝、停用、解绑和并发变更。
- 邀请：使用数据库并发测试验证最后一次使用不会超发，Redis 限流测试不能代替事务测试。
- 同步：覆盖空间切换、重复操作 ID、游标隔离、引用越界、离线积压、撤权和多设备字段冲突。
- 管理后台：覆盖 Cookie 属性、CSRF、CSP、会话固定、暴力登录限流、输入转义、越权 ID 和敏感信息泄漏。
- 客户端：对工作空间选择器、升级迁移、离线读写、撤权恢复区和 Android/Windows 主流程增加永久自动化测试。
- 供应链：锁定依赖版本，执行 Go 和 Dart 静态检查，CI secrets 只来自运行环境，构建产物生成版本和提交标识。

## 6. 尚需确认的边界情况

以下问题尚未从需求中唯一确定。括号内是建议默认值；标记为 P0 的项目必须在对应版本开工前定案，P1 可按建议先实现并在 beta 前复核。

| 优先级 | 边界问题 | 建议默认值 | 最晚确认点 |
| --- | --- | --- | --- |
| P0 | 协作关闭时，群组任务对谁可见？ | 仅任务所属群组账号可见；L2 只管理成员关系，不默认读取成员任务正文 | `alpha.4` 前 |
| P0 | 开启协作后，共享范围是全群组还是指定成员？ | MVP 只支持“明确共享给全群组”；指定成员 ACL 延后 | `alpha.4` 前 |
| P0 | L2 直接绑定已有真实账号是否需要对方确认？ | 管理员可直接绑定，但必须使用精确账号标识、通知被绑定人并允许其退出；重绑需要二次确认 | `alpha.2` 前 |
| P0 | 成员退出、解绑或被停用后，其群组任务归谁？ | 任务仍归原花名册账号；群组至少一名 L2 可重新指派，历史操作者不改写 | `alpha.4` 前 |
| P0 | 谁可以创建群组？ | 任意有效真实账号可创建，并自动成为该群组首个 L2；可通过服务器配置关闭自助创建 | `alpha.2` 前 |
| P0 | 第一个 L3 如何产生和恢复？ | 使用一次性 CLI 引导；恢复必须通过服务器主机访问和审计，不提供公开网页提权入口 | `alpha.2` 前 |
| P0 | 真实账号如何创建、停用和删除？ | MVP 由 L3 创建/停用，不开放公开注册；停用可逆，物理删除延后 | `alpha.2` 前 |
| P0 | L2 能否创建或邀请另一个 L2？ | 可以，但邀请码默认加入为 L1；升为 L2需单独确认和审计 | `alpha.3` 前 |
| P1 | 用户是否可以主动退出群组？ | 可以；最后一个 L2不能直接退出，必须先移交或由 L3 接管 | `beta.1` 前 |
| P1 | 个人任务能否移动到群组，群组任务能否移回个人？ | MVP 提供“复制”，不做跨空间原地移动，避免引用和审计失真 | `beta.1` 前 |
| P1 | 群组、花名册名称是否唯一？ | 群组名服务器内可重复；花名册显示名可重复，另设群组内唯一稳定编号 | `alpha.2` 前 |
| P1 | 邀请次数是否设置数值上限？ | 数据库使用正整数；API 配置合理上限以防误操作，默认建议 10,000 | `alpha.3` 前 |
| P1 | 到期时刻如何判定？ | 全部使用服务器 UTC；当 `now >= expires_at` 时失效，客户端时间不参与授权 | `alpha.3` 前 |
| P1 | 账号停用或改密后现有会话如何处理？ | 立即撤销全部刷新令牌和管理会话；短期访问令牌通过状态复查或很短 TTL 收敛 | `alpha.2` 前 |
| P1 | 审计日志保留多久、谁能看？ | L3 查看全局，L2 查看自己群组；MVP 默认长期保留，仅支持导出和运维归档 | `beta.2` 前 |
| P1 | `/KairosAdmin` 是否允许补斜杠跳转？ | 仅 `/KairosAdmin/` 为入口；不对其他拼写或大小写提供重定向 | `beta.2` 前 |

如果采用上述默认值，数据库设计应提前保留 `task_owner_group_account_id`、`visibility`、稳定花名册编号、绑定有效期和操作者字段，避免在协作阶段再次进行高风险重构。

## 7. Definition of Done

每个增量版本只有同时满足以下条件才算完成：

- 功能、失败路径、授权范围和并发边界均有自动化测试。
- 数据迁移已在空库和上一发布版本样本库验证，且有明确回滚方式。
- API 文档、错误码、部署配置、监控和运维手册同步更新。
- 日志、错误响应和管理页面不泄露密码、令牌、原始邀请码或跨群组数据。
- Go 格式化、静态检查、单元及集成测试，Flutter analyze、单元/组件/集成测试和目标平台构建全部通过。
- 代码评审明确检查工作空间隔离、角色作用域、事务原子性和 Redis 降级行为。
